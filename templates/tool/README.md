## Quick start

```sh
pnpm install
pnpm run build                 # tsc → dist/index.js (pure ESM)

# From the PARENT directory, install into a profile and boot:
dsh plugin --profile my-profile add ./{{PKG_NAME}}
dsh --profile my-profile       # watch for: [{{PLUGIN_ID}}] registered "{{TOOL_NAME}}" — listed=true
```

> `dsh plugin add <dir>` anchors relative paths to the invoking directory — run it from the plugin's parent directory.

## Configure

```yaml
- id: {{PLUGIN_ID}}
  config:
    defaultGreeting: Good morning
```

A patch **replaces** the whole `config` rather than merging keys, so restate every key the row needs.

## What to check before shipping a tool

- The `description` reads from the model's side — task vocabulary only, no UI or transport terms.
- Every parameter the model must supply is marked `required: true`.
- `output.schema` describes exactly what `execute` returns; `render` is a pure function of it.
- The tool disposes with the plugin (registration is an effect — this template already does it).

Booting the profile and seeing `listed=true` proves registration. Having the model actually
call the tool needs `DEEPSEEK_API_KEY`; without one the call fails with `MISSING_CREDENTIAL`.

## Dependencies pinned

Every `@deepseek-ai/*` package sits in `devDependencies` because it is **build-time types only**:
at runtime the plugin binds to the copies inside the running harness, resolved through
`$DSH_HOME/profiles/node_modules`. Declaring them as real dependencies installs a second copy —
harmless for a pure helper like `defineTool`, fatal for anything identity-sensitive.

- `@deepseek-ai/cordis`: `^{{CORDIS_VERSION}}`
- `@deepseek-ai/schemastery`: `^{{SCHEMASTERY_VERSION}}`
